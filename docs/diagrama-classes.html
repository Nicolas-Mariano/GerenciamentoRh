AumentoDecorator“Decorator abstrato: guarda uma CalculadoraSalario e delega a ela (envolve outro cálculo).”

IFuncionarioDAO / ISetorDAO / IEnderecoDAO + impls“CRUD via JDBC. Versões com e sem Connection permitem participar da transação do service. Cada impl tem getConexao() e auxiliares popular*.”

modelFuncionario“Dados pessoais permanentes (nome, cpf, telefone, email) + desligado. Guarda 1 Endereco (composição). Tem Builder e formatações (cpf/telefone).”

3) Os fluxos principais (roteiro de leitura)

  • Cadastrar funcionário + 1º contrato: JSP → ControllerServlet → CadastrarFuncionarioAction → FuncionarioServiceImpl.cadastrar() (transação: EnderecoDAO + FuncionarioDAO) → depois ContratoServiceImpl.contratar() grava o contrato.
  • Aplicar promoção: Action → ContratoServiceImpl.aplicarPromocao() valida nível superior e calcula o novo salário pelo Decorator (SalarioBaseContrato + AumentoPercentual/AumentoPorBonus) → ContratoDAO.atualizarPromocao().
  • Demitir: Action → ContratoServiceImpl.demitir() (valida data, contrato não encerrado) → ContratoDAO.atualizar() grava data e motivo.
  • Recontratar: Action → ContratoServiceImpl.recontratar() (sem contrato ativo; nível ≥ e salário ≥ +10% do último) → novo Contrato.
  • Vincular gerente: Action → SetorServiceImpl.vincularGerente() (contrato do setor, ativo, Pleno/Senior) → SetorDAO.atualizar().
  • Listagens: Actions de leitura (ex.: ListarFuncionariosAction) chamam o DAO direto, sem service — não há regra de negócio.
  • API REST: /api/... → Resource (JAX-RS) → mesmos ServiceFactory/DAOFactory.

4) Os padrões de projeto (frase para cada um)

  • Front Controller — um único servlet recebe todas as requisições.
  • Command — cada ação é uma classe com executar(); fácil adicionar novas ações.
  • Factory — ServiceFactory/DAOFactory criam objetos retornando interfaces (baixo acoplamento).
  • Reflexão — o servlet monta o nome da classe a partir do parâmetro acao e a instancia dinamicamente.
  • Builder — Funcionario/Contrato/Setor/Endereco são montados de forma fluente (.comX(...).constroi()).
  • Decorator — AumentoPercentual/AumentoPorBonus envolvem SalarioBaseContrato para compor o cálculo do salário.
  • DAO / Repository — isola o acesso ao banco; o resto do sistema não vê SQL.
  • Service Layer — concentra regras de negócio e transações, separadas da persistência.

Notas de domínio

  • Funcionário × Contrato (1—N): dados pessoais ficam em Funcionario; cada vínculo é um Contrato (salário, datas, nível, setor). Demissão e recontratação não apagam registros — preservam o histórico.
  • Composição Funcionario◆Endereco: endereço não vive sem o funcionário (gravados juntos na transação de cadastro).
  • Agregação Contrato◇Funcionario / Contrato◇Setor: o contrato referencia funcionário e setor, que existem independentemente.
  • Gerente do setor (Setor.contratoResponsavel): só um contrato ativo de nível Pleno/Senior do próprio setor pode assumir.
  • Decorator de salário: a promoção calcula o novo salário compondo SalarioBaseContrato com AumentoPercentual ou AumentoPorBonus; exige nível estritamente superior ao atual (NivelSenioridade.ehInferiorA).
  • Recontratação: exige nível ≥ ao do último contrato e salário ≥ 10% acima do anterior.
  • nomeResponsavel (Setor) e nomeFuncionario (Endereco) são campos de projeção (JOIN para a View), não associações.
  • API REST (/api/...) coexiste com o fluxo Servlet/JSP e reutiliza as mesmas regras via ServiceFactory/DAOFactory.
